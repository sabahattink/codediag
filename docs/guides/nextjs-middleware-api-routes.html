Is your Next.js middleware protecting your API routes?

Updated November 2, 2026 · Next.js 13–16, App and Pages Router

Only for the paths its matcher covers and the branches that reject. Three gaps are common: a matcher that skips /api, a session check inside a path branch for another section, and auth middleware that loads the session but never blocks.

Next.js's own authentication guide says middleware (called proxy since Next.js 16) shouldn't be your only line of defense. Verify the session in each route handler.

Three ways middleware misses API routes

3. The middleware reads auth but never enforces it

export default clerkMiddleware() makes the auth state available to your routes, but doesn't reject a request until you call auth.protect() or check auth yourself. Clerk's docs now recommend protecting access as close to the resource as possible. The same goes for any middleware that only refreshes a session cookie.

Why middleware shouldn't be the only check

Next.js's authentication guide calls middleware an optimistic check that shouldn't be your only line of defense, and says to verify authentication as close as possible to your data. It also says to treat Server Actions like public API endpoints.

There is a concrete reason. In 2025, CVE-2025-29927 let a request header make self-hosted Next.js skip middleware entirely. It was fixed in 15.2.3, 14.2.25, 13.5.9, and 12.3.5. Apps whose only auth check lived in middleware had every route behind it open.

Questions

Does Next.js middleware run for API routes?

Only for paths its matcher covers. Without a matcher it runs on every request; a matcher that excludes api skips every route handler under /api.

What changed in Next.js 16?

The middleware file convention was renamed to proxy (proxy.ts). Matchers work the same way, and the advice to verify auth close to the data still applies. CodeDiag reads both files.

Does clerkMiddleware() protect my routes?

Not on its own. It doesn't reject a request until you call auth.protect() or check auth yourself, and Clerk recommends protecting access close to the resource.

What about Server Actions?

Next.js's authentication guide says to treat them like public API endpoints and verify authentication and authorization inside each one.
