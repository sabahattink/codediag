Does an auth check in +layout.server.ts protect SvelteKit form actions?

Updated November 2, 2026 · SvelteKit 2

No. A redirect in a layout's load doesn't stop a form action or a +server endpoint under that layout. SvelteKit runs the action first and the load functions after it, and +layout files have no effect on +server.js.

Check auth in the handle hook in src/hooks.server.ts, or at the top of every action and endpoint.

Why the layout check comes too late

When a form posts to ?/delete, SvelteKit handles the request in this order:

  1. The handle hook runs.
  2. The action runs and does its work: here, it deletes a user.
  3. The page's load functions run to render the result. The layout's redirect fires now, after the delete.

The SvelteKit docs describe both halves: load functions run after the action completes, and handle runs before the action is invoked.

Endpoints are worse off. The routing docs say +layout files have no effect on +server.js files; per-request logic belongs in handle. Even for page loads, SvelteKit runs load functions concurrently, and its notes on authentication recommend hooks for protecting a group of routes.

Fix it

Reject anonymous requests in handle

Best when a whole section of the app needs a signed-in user. It covers pages, actions, and endpoints under the path in one place.

If you protect a route group such as (app) rather than a path prefix, test event.route.id instead. Keep the layout redirect if you like the user experience; it just isn't the security boundary.

Questions

Does a +page.server.ts load protect the same page's actions?

No. The action runs first and the page's load functions run after it completes, so a redirect in the page load also comes too late.

Does handle run for form actions and +server endpoints?

Yes. It runs for every request the server receives, before the action is invoked. That is why it is the place to reject anonymous requests for a group of routes.

Isn't SvelteKit's CSRF protection enough?

No. The origin check stops other sites from submitting forms in a victim's browser. A script that sends the request directly can set any Origin header, so the action still needs an auth check.

Can an auth check in +layout.ts protect anything?

No. Universal load functions also run in the browser, so they are never a security boundary.
